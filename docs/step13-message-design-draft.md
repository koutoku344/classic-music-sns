# STEP13 メッセージ — 現状調査と初期実装方針

## STEP12からの引き継ぎ
- 募集は全ユーザー公開、応募は pending → 主催者の承認/却下。
- **承認された応募の相手同士が、STEP13で連絡できるようにする**。
- 募集の音声添付は仕様外。メッセージでのファイル添付も初期範囲には含めない。

## 既存コード
- `features/sonolii/screens/Messages.tsx` は `data.ts` のサンプル会話を使用。
- `features/sonolii/screens/Conversation.tsx` は固定文＋ローカルstateで、API送信なし。
- `app/messages/*` に画面ルートはある。Backend/DBの会話テーブルは現段階で存在しない。

## 推奨MVP設計
- 承認済みの `recruitment_applications` を起点に、募集主催者と応募者の一対一会話を作成する。
- 1応募につき1会話を保証（UNIQUE application_id）、会話参加者2人のみ閲覧・送信可能。
- 募集主催者・承認済み応募者のいずれも会話を開始可能。未承認・却下・第三者は不可。
- メッセージはテキストのみ（1〜2000文字）、送信後の編集・削除なし。
- 新着/未読は参加者ごとの `last_read_at` を用いて管理。会話/メッセージ一覧はカーソルページング。
- 会話は応募と紐づける。募集を削除するときの会話履歴保持・削除ポリシーは実装前に確定。
- フォロー関係からのDM開始は初期範囲外。将来追加するなら同意・ブロック・スパム対策を検討する。

## 工程とテスト
1. migration 025とBackendの認可処理／Frontend API化をまとめて実装。
2. 静的・mock handler・型・ビルドを `npm run test:step13:check` に集約。
3. Neon適用→Backend/Frontendデプロイ→読み取り確認。
4. A/B専用募集・承認済み応募を使う書き込みE2Eを別コマンドで実行し、専用データだけを後片付け。
5. 最終レビュー後mainにマージ。

## 決定が必要な論点
- 募集を主催者が削除した場合、会話履歴は残すか（推奨）、紐づけて削除するか。
- 同じ2人が別募集で承認された場合、募集ごとに会話を分けるか（推奨）、統合するか。

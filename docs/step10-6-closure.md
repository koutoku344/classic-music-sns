## 3. 未検証・リリース前に検討が必要な項目

1. 429 Rate Limitの**発動確認**は本番Workerの大量リクエストを避け、隔離環境で実施。アカウント単位の公平性、Cloudflareの地域分散下の制限精度、誤検知を確認する。
2. コメント削除と返信作成の競合、いいね・投稿削除との競合、DB行ロックの待機・解除を独立した接続で実測。既存投稿・コメントを使って破壊的負荷試験は行わない。
3. 認証前・GET大量アクセスは現在のフィードバックRate Limiting bindingの対象外。WAF等の防御・コスト上限を正式リリース前に設計する。
4. 退会時の`users` CASCADE削除により、他ユーザーの返信が失われる可能性がある。退会フロー実装時に匿名化・墓石モデルなどを設計する。
5. 旧ドキュメントの概念モデル（Performanceや旧API経路など）は段階的に更新中。設計書の末尾にあるSTEP8/9/10実装済み節を優先する。
6. STEP8/9引継：R2認証情報TTL（現状Forever）、更新／再取得設計、R2容量・Class A/B費用、Cronの実実行、Neon/R2部分障害復旧、署名URL期限切れ時の更新・再取得の確認。

## 4. STEP10-6 mainへの反映（WSL）

前提：GitHubで`feat/step10-feedback`の設計書反映を確認し、ユーザーがマージ実施を判断すること。

```bash
cd ~/classic-music-sns
git switch feat/step10-feedback
git pull origin feat/step10-feedback
git status
npx tsc --noEmit
npm run build
```

エラーがあればマージしない。`git status`に未コミットの変更があれば内容を確認し、失われないようにする。

GitHubで`feat/step10-feedback` → `main`のPull Requestを作成し、差分とCIを確認したうえでマージする。GitHub上の実際のマージ完了を確認できるまで、STEP10-6の最終状態を「マージ済み」と記載しない。

マージ後：

```bash
git switch main
git pull origin main
git status
```

※既存データは削除しない。適用済みSQL016〜018を再実行しない。本書の作成はデプロイ・マージを行わない。
